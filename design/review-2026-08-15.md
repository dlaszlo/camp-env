## Corrections the measurements force on the settled record

Four entries. Everything else in Parts A, B and D held up.

### 1. C19's conclusion is wrong — the docker gate works inside the rootless mode

C19 (*read*) says supplementary groups are lost inside an unprivileged
user namespace, so access depending on the `docker` group does not work.
B11's appended note carried that into the mode question: "the blocker was
never root — it is group membership."

Measured, inside `ply run`: `/proc/self/status` shows
`Groups: 65534 65534 … 0`; the docker socket stats as `nobody nogroup`;
**and `docker ps` succeeds** against the default unix socket — it listed
the soak container actually running on this machine — `docker version`
reaches server 29.4.1, and `/var/log/syslog` (`root:adm 0640`) is
readable.

What is actually true: `setgroups` is denied — that half of C19 stands —
so the groups cannot be *changed* and have no in-namespace identity. But
the kernel credential **retains** the real supplementary groups, and
host-filesystem permission checks keep honouring them. "Lost" should read
"frozen and unmappable, but still effective".

Consequence for C2: **the pre-push docker gate runs inside the rootless
mode.** The largest workflow cost previously attributed to that mode does
not exist. B11's settled decision (docker needs no root; podman planned)
is untouched — the podman migration stays worthwhile on its own merits;
it is no longer what the mode decision waits on.

### 2. C11 holds at the syscall, not at the tool

A one-invocation `mount --bind -o ro` produced a mount whose per-mount
options read `ro` and which refused a write (*measured*) — modern
util-linux performs the second step itself. The constraint is real for a
program issuing raw `mount(2)`, where one call with `MS_BIND|MS_RDONLY`
still silently ignores the `ro` — which is what a Go implementation does.
The design consequence is unchanged and now sharper: **read-onlyness is
verified by looking at the result, never trusted from the call** (C1
below).

### 3. C9 softens on this kernel, and C5 is half-measured

An overlay mounted in the user namespace **without** `userxattr` came up
with `userxattr` in its super options anyway — the kernel added it,
along with `redirect_dir=nofollow` and `uuid=on` (*measured*). On that
mount: copy-up set `user.overlay.origin` on the file and
`user.overlay.impure` plus `user.overlay.uuid` on the upper directory;
deleting a lower file left the `0:0` character-device whiteout (C4);
deleting and recreating a lower directory set `user.overlay.opaque` (all
*measured*).

So the feared shape — "mounts, then misbehaves around whiteouts" — does
not exist on 7.0.0-29, and **C5 moves from assumed to measured for the
namespace mode**: the forensic marker is real and lives in `user.*`
there. The `trusted.*` side remains unmeasured until the first privileged
`up`. Two consequences: `doctor`'s copy-up forensics must ask both xattr
namespaces; and option verification must compare **per option**, not by
string equality, because the kernel appends options nobody passed.

### 4. New constraint, measured: locked mount flags — the rootless mode fails on `/tmp`

The first lab was built under `/tmp` and `ply run` failed at its first
step: *"making workspace read-only: operation not permitted."* `/tmp`
here is tmpfs mounted `nosuid,nodev`; inside a user namespace those
flags are **locked**, and a `remount,bind,ro` that does not carry them
forward gets `EPERM`. The identical lab on ext4 (`rw,relatime`, nothing
locked) worked. Both halves *measured*; the mechanism *read* from the
mount API's semantics.

Proposed for `constraints.md`:

> **C34. A read-only remount inside a user namespace must preserve the
> source mount's locked flags** (`nosuid`, `nodev`, `noexec`, atime
> flags) **or it fails with `EPERM`.** *(measured, by failure on tmpfs
> and success on ext4)*

It is also a bug in the current binary's namespace mode, and a `doctor`
check: an environment directory on a nosuid filesystem breaks the
rootless mode until the remount copies the flags.

## C1 — what `up` verifies about its own mounts, and refuses on

`ply` performs the mounts, so `ply` checks them, on the real machine, at
every start (B9). Two measured facts shape the whole list:

- **Presence in `/proc/self/mountinfo` does not prove reachability.** A
  read-only island was bound inside a directory, then the directory was
  covered by a second bind: the island's marker file became unreachable
  by path while mountinfo **still listed the island's mount**, and
  `statvfs` on the path reported the cover's read-write, not the
  island's read-only (*measured*). A mount can be alive and invisible.
- **Path-based syscalls see exactly what a process would see.** On the
  lab composition, `statvfs` by path reported `live` and `live/.git`
  writable and `live/docs`, `live/CLAUDE.md`, `live/.claude` read-only,
  matching the plan; `stat` on `live/.claude` and on
  `workspace/.claude` returned the same `(st_dev, st_ino)` (*measured*).

So the verification's primary instrument is the **path**, with mountinfo
as the cross-check — not the other way round.

### Before any mount — static refusals

Cheap, and they run while the composition is down, when repair is safe
(A4's property):

1. **Order validation** (B6's missing half): refuse a declared order in
   which an earlier mount's target lies inside a later mount's target —
   the later one would cover it silently, which is the measured shadowing
   above. O(n²) path comparisons over a dozen entries.
2. **Targets inside the tree**: every mount target resolves under the
   merged root (the exclude's target `live/.git/info/exclude` included);
   anything else is refused.
3. **Target exists and types match** (C10, C13): file onto file,
   directory onto directory. Targets that ply's own storage provides
   (the `.claude` store's placeholders, C3) are created in storage
   first — its own storage, so no repository is written.
4. **Sources exist and are not symlinks** (C12); a root entry that is a
   symlink blocks via the inventory (A12/§8).
5. **Workdir constraints** (C6): same `st_dev` as the upper, and — new,
   correction 4 — in the namespace mode the source mount's locked flags
   are replicated on every read-only remount.
6. **The composition lock** — its own subsection, because it is the one
   check that cannot be a mountinfo scan.

### The composition lock (C8)

Measured, twice over: the kernel **mounted a second overlay onto the same
upper without complaint**, and the current binary **ran two concurrent
compositions on the same upper**, each in its own namespace — the exact
state C8 calls data-corrupting. In the rootless mode no mountinfo scan
can ever catch this, because the other composition's mounts live in a
namespace this process cannot see (C20).

The guard that covers both modes is a file lock on the shared filesystem
— `flock` is inode-based and crosses namespaces:

- a lock file derived from the **upper's real path** (e.g.
  `$ENV/.ply/lock.<upper-hash>`), taken `LOCK_EX | LOCK_NB`;
- **rootless**: the session-leader process holds it for the
  composition's lifetime, so it dies exactly when the namespace does
  (C21) — no staleness possible;
- **privileged**: no process outlives `up`, so the lock is held only
  across the `up` and `down` transitions, and the steady-state guard is
  the machine-wide mountinfo scan for an overlay with the same
  `upperdir`.

The four pairings close (*reasoned*): rootless-then-rootless, the flock;
rootless-then-privileged, the flock (still held by the live session);
privileged-then-privileged, the scan; privileged-then-rootless, the scan
— a new namespace inherits a copy of the host mount table, so the
privileged composition's overlay is visible in it.

### After mounting, before declaring the composition up

For every planned mount, in this order:

1. **Reachability and identity, by path.** Binds: `stat(target)` equals
   `stat(source)` in `(st_dev, st_ino)` (*measured primitive*). The
   overlay: `statfs(live)` has the overlay magic, and the mountinfo
   entry *at* `live` carries `lowerdir`/`upperdir`/`workdir` equal to
   the plan — compared per option, since the kernel appends its own
   (correction 3). This single check also catches every ordering
   mistake the static validation might miss, because a shadowed mount
   fails it (*measured*).
2. **Writability polarity, by path.** `statvfs` `ST_RDONLY` must match
   the plan for every target (*measured on the lab composition*). This
   is what catches the raw-syscall one-step bind (correction 2) — the
   result is inspected, the call is not trusted.
3. **The exclude, by content.** Read `live/.git/info/exclude` and
   require the generated marker line. In the lab, the bind on the live
   path read back the generated bytes while `code/.git/info/exclude`
   kept the repository's own content (*measured*, and the basis of C4's
   target decision below).
4. **Propagation.** Every ply mount private: empty optional-fields in
   its mountinfo entry (*measured* inside the namespace, where the root
   is private by construction; under `ply up` this machine's `/` is
   `shared:1` — *measured* — so C14 applies with full force and each
   mount is made private and then verified).
5. **No strangers, nothing missing.** The set of mountinfo entries under
   the live prefix equals the plan exactly — fewer means a failed mount,
   more means crash residue or outside interference.
6. **Storage ownership.** Storage paths stat as the invoking user
   (`SUDO_UID` under the privileged mode — B12). In the namespace mode
   this is automatic and was confirmed in passing: the kernel's leftover
   `work/` came out owned by the user, mode 000 (*measured*), so even
   that residue is the user's to remove.

**On any failure: unmount in reverse order, name the failed check, exit
non-zero.** `up` may refuse, and this is where it does. If the reverse
teardown itself fails — something wandered in mid-`up` — the state is
reported as *partly up* with the holder named from `/proc/*/cwd` and
`/proc/*/fd` (C16, C30), never guessed from `fuser` or parsed from a
translated message (C29, C30).

### Where each check lives

| check | where | why |
|---|---|---|
| static refusals, lock, post-mount verification | **`up`, every run** | a few dozen syscalls and one `/proc` read; there is no cost argument against it |
| the same verification, read-only, reported not refused | **`status`** | "is it still the composition I built" is the question `status` exists for; one code path, two exits |
| machine capability (namespaces, sudo), locale, nosuid environment (correction 4), whiteout-and-opaque probe in a throwaway overlay per mode, copy-up forensics in both xattr namespaces | **`doctor`** | environment properties, not composition properties; some need a scratch mount |
| the thirteen-write attack battery (`04-copyup-negative.txt`) | **nowhere** | it measures the kernel, not the composition; the kernel was measured once in the POC and again in this lab (append, create, delete all refused). Per-run, the polarity check above asserts the same property in one syscall per mount |
| byte-manifest and strace harnesses | **nowhere** | settled by B7/B8. The lab confirmed the design claim once from outside: a full session left the lower byte-identical (seven files, sha256) and zero mounts behind |

### Optional hardening: build at a staging path, `mount --move` into place

`mount --move` of a tree carries its submounts (*measured*), so the
composition can be assembled and verified at `work/<hash>/staging` and
made visible at `live/` only after every check passes. In the rootless
mode this buys nothing — no process outside the namespace ever sees an
intermediate state (C20). Under the privileged mode the window between
first mount and verification is machine-visible, and the move closes it.
Worth having when the privileged path is built; not a precondition.

### The invariant's guard in the source (B8)

Whether `ply` writes into a repository is a property of its source: 18
filesystem-write call sites across 7 files today (*measured*, by grep).
One of them is exactly the class the redesign outlaws:
`gitwire.InstallExclude` does `MkdirAll` and `WriteFile` on
`code/.git/info/exclude` (*read*) — the old design, which the redesign
replaces with the mounted temp file. The guard to keep as the code
changes: filesystem writes live in one package, and no write target may
be derived from a repository path; a reviewer checks the write sites,
not a harness.

## C2 — the mode

B13's deciding question: must programs started outside the composition
see the tree? The measurements move the answer substantially.

**What measurement removed.** The docker gate was the concrete workflow
that seemed to force the privileged mode, and it works inside the
namespace (correction 1). Pushing to main from inside the rootless
composition is not blocked by the mode. (The pre-push hook also never
needs `dockerd` to see the live tree: it tests a `git archive` copy in a
temp directory, not the working tree — *read*, from the hook's source,
in the first attempt.)

**What actually runs outside, on this machine, today** (*measured*):
Sublime Text and Nautilus are running now; VS Code is installed; the
session is a Wayland desktop; `dockerd` and `containerd` run as system
daemons; podman and `newuidmap` are absent. So the honest answer to the
deciding question is: **yes for the GUI editor and the file manager, no
for everything else measured.**

One trap inside the "start it from inside" answer (*reasoned,
unmeasured*): a single-instance GUI editor defeats it. `ply run -- code
live` hands the path to the already-running outside instance, which
opens the raw directory, not the composition. An editor like that is
usable with the composition only under `ply up` — or by closing it
first, which is not a workflow.

**What the rootless mode still costs, measured here:**

1. **One entry per namespace.** Each `ply run` builds its own namespace
   and its own composition — two concurrent runs did exactly that
   (*measured*), which is both the C8 hazard (the lock, C1) and the
   wrong shape for a multi-terminal workflow. The POC's own evidence
   shows the owner working from several terminals against one tree
   (`21-live-down-worktrees.md`). For the rootless mode to serve that,
   `ply` needs join machinery: a pilot process that holds the
   namespaces for the composition's lifetime, and `ply shell` entering
   it via `setns` — the model podman's pause process uses (*reasoned*;
   the mechanism is proven there, not built here). Teardown stays free:
   kill the pilot and C21 does the rest.
2. **Locked flags** (correction 4): broken today on nosuid filesystems;
   a code fix.
3. **uid 0 cosmetics.** Inside, `id` says root and files stat as the
   single mapped user (C18, *measured*). Git works — a full
   commit-status cycle ran in the lab. Whether the agent tooling
   objects to running as apparent root (Claude Code refuses some flags
   as root) could not be measured in this session — the probe was
   blocked by the session's own policy — and is a one-command check to
   run before committing.
4. **Forensics differ per mode** (correction 3): `user.*` here,
   `trusted.*` under root; `doctor` must know both.

**What the privileged mode costs, unchanged by measurement:** a password
at `up` and at `down`, typed in a real terminal (C33 — no scripting); a
machine-wide blast radius for any mistake; the whole `down` state
machine — holders (C16), partial teardown, crash residue, the
"0 unmounted, 8 were not mounted" class of bug; root-owned artifacts to
hand back (B12); and the mount-then-verify window being publicly visible
(the staging move exists to close it).

**What the rootless mode buys, measured in one session:** teardown that
cannot fail (exit; zero mounts remained), no state record needed (`ply
list` gained none), the lower byte-identical afterwards (B7's meaningful
half, confirmed from outside), user-owned residue only, and no password
ever.

**Recommendation.** Make the rootless mode the primary one, and keep
`ply up` documented for the sessions where an outside-started program
must see the tree — today that is the GUI editor, and nothing else
found. Named preconditions, each its own piece of work:

- (a) the pilot-and-join machinery, without which rootless is
  single-entry and does not fit the demonstrated workflow;
- (b) the composition lock (C1) — needed in both modes, sharpest here;
- (c) the locked-flags remount fix (correction 4);
- (d) the one-command check that the agent stack runs under an apparent
  uid 0.

If (a) is judged too much machinery for what it buys, the honest
fallback is privileged-primary — single-entry rootless is not a smaller
version of the workflow, it is a different workflow. B13 remains the
owner's call; this section is input, not a decision.

## C3 — `.claude/`, once it has left the code repository

Measured today, both sides. The workspace tracks four entries under
`.claude`: `agents/`, `output-styles/`, `skills/`, `settings.json` — 14
files. Untracked beside them: `commands/` (empty), `scheduled_tasks.lock`,
`settings.local.json`. The code repository tracks only
`.claude/settings.json`; untracked beside it: `settings.local.json`,
`worktrees/`. So the observed runtime-name set is
`settings.local.json`, `worktrees/`, `scheduled_tasks.lock`,
`commands/` — small, but it already contains a name no document
predicted (`scheduled_tasks.lock`), which is the premise "the runtime
names cannot be enumerated in advance" confirmed rather than assumed.

**The shape is not a choice — §10.3's sketch is the only legal one.** A
machine-local *file* (`settings.local.json`) can never exist in a
repository, so there is nothing to bind a writable hole onto (C10); and
creating the placeholder through the overlay would copy `.claude` up
into the code repository, which the invariant forbids. The only shape
that provides attachment points without writing a repository is:

1. `mount_rw` **store over `live/.claude`** from
   `storage/<live-hash>/.claude` (mirrored path, A6) — first, by order;
2. **read-only islands inside it** for each entry the workspace
   contributes: today `agents`, `output-styles`, `skills`
   (directories), and `settings.json` — a file, so ply first creates an
   empty placeholder file in its own store to bind onto (file-on-file
   binds work, *measured*).

What this yields: every unpredicted runtime name lands in the store —
machine-local, persistent (storage is never removed, so approvals and
worktrees survive sessions); the workspace's own runtime junk
(`scheduled_tasks.lock`, its `settings.local.json`) never appears in the
tree, because the store covers the raw lower directory entirely; and a
write to an island fails with `EROFS` instead of copying up.

**The island list is derived, not configured** — from what the workspace
tracks under `.claude`, which is one `git ls-tree` (reading, allowed by
A9) and belongs to the same enumeration step as the exclude (C5). Two
edges to state: a tracked entry added mid-session is absent until the
next `up` (same staleness class as the exclude; `up` prints the island
list); and an island whose source disappears blocks at the next `up`
via the inventory.

Cost today: one store plus four islands, five mounts. The gate never
sees `.claude` — it is a mount target, exempt (B5) — and the exclude
carries the one line `/.claude`.

## C4 — the exclude: derivation, and the target A7 left open

**Derivation: coarse-by-name, anchored — recommended, with A8's thread
closed honestly.** The sizes (*measured*): the workspace tracks 3,183
files against 15 tracked root entries (19 raw); in the steady state the
root is roughly five names. The deciding axis is what happens
mid-session, because the gate cannot re-check until the next `up`:

- **Coarse (`/name` per lower root entry):** a file the workspace gains
  inside a covered name is covered automatically — no leak window. A new
  *root* entry is caught by the gate at the next `up` (§5 already says
  so).
- **File-by-file (3,183 lines):** a file the workspace gains mid-session
  matches no line, appears untracked in the live tree, and `git add .`
  stages it into the code repository — the exact leak the tool exists
  to prevent, in the window the tool cannot see. Its real advantage — a
  reviewable inventory of what the lower contributes — is already
  provided by §8's inventory file.

So coarse wins on the tool's own axis. But A8 records that the owner
asked for file-level twice and never accepted coarse; §5 wrote coarse in
anyway. The recommendation here is coarse **as a proposal to bless, not
a fact to inherit** — with the leading `/` that the owner's file-level
version had by construction (any pattern containing a separator anchors
itself; a bare name matches at every depth — Part D). The current
binary, for what it is worth, already anchors its generated lines with
`/` (*read*, `gitwire.ExcludeBlock`); the unanchored form was a §5
wording bug, not an implemented one.

Mechanics, all from Part D: escape `\`, `[`, `]`, `*`, `?` and a
trailing space; `#` and `!` need nothing once the `/` leads the line; a
name containing a newline cannot be expressed and is **refused** (it
also blocks in the inventory). File-level enumeration survives only
inside allow-listed directories, of which the steady state has none —
the expected `allow_overlap` is `.gitignore`, a file, and file overlaps
do not descend.

**The target: `live/.git/info/exclude` — now measured, and settled by
the measurement.** A7 deliberately left the mount target unstated. In
the lab, a file bound onto `live/.git/info/exclude` (on top of the
`.git` bind) read back the generated content through `live/` while
`code/.git/info/exclude` kept the repository's own bytes through the raw
path; `git status` run in the live tree honoured the generated list
while `git status` in `code/` did not (*measured*). So the mount scopes
exactly as wanted: the composition sees it, the raw repository and any
checkout registered outside do not. Worktrees under
`live/.claude/worktrees` resolve their common git directory through the
live path and therefore see the generated list too — intended (B10),
and harmless with anchored lines and zero overlap. Under the privileged
mode this scoping is not a preference but the difference between a
composition detail and a machine-wide change to what `git status`
reports in `code/`.

Content of the mounted file, per A7 point 4: the upper's existing
`.git/info/exclude` as the base, plus the generated block, plus a marker
line — the marker doubles as C1's read-back check. If `.git/info` or
the file does not exist (possible: a repository from an empty template
lacks both — Part D), `ply` refuses and prints the two commands
(`mkdir -p .git/info && touch .git/info/exclude`); creating them would
write the repository. The user acts; `ply` checks (A11).

## C5 — externalising the exclude generation

The contract that takes git out of the core (A14), in one paragraph per
open point:

**Shape.** At the `prepare` phase, the core materialises its inputs into
`work/<hash>/`: the lower's root listing with types, the mount-target
list, `allow_overlap`, and the upper's current exclude content. The
configured step consumes them and writes two outputs: the exclude
payload and the `.claude` island list (C3) — the two places git
knowledge lives. The core validates the marker and mounts the file. A
built-in git implementation ships as the default step, so configurable
never means obligatory.

**Privilege.** Configured steps run as the invoking user, always. The
clean way to get that in both modes is the phase order: `prepare` runs
*before* any privilege or namespace transition — under the privileged
mode before sudo is exercised, under the rootless mode before the
namespace exists — so there is nothing to drop. A step that must run
later (`mounted`, `pre-down`, `down`) runs with privileges dropped to
`SUDO_UID`/`SUDO_GID` under the privileged mode, and `ply` refuses to
run it if dropping fails. Whoever edits `config.yml` must never gain
root through it.

**Phases.** `prepare` (generate; before anything), `mounted` (after
verification, before the composition is declared up), `pre-down`,
`down` (after teardown, for reporting). Four, no more until a real step
needs a fifth.

## C6 — what `down` and `doctor` report

`down` — report, never refuse (A11), and never delete:

1. **Worktrees registered under the live path**, each with its exact
   recovery: `git -C <code> worktree repair <storage-path>`, and the
   three-month `gc.worktreePruneExpire` window named — the one failure
   that happens while nobody is looking (Part D).
2. **Drift and suspected leaks, while the cause is fresh**: the gate's
   comparison re-run and reported; plus the code repository's untracked
   paths whose first component matches a lower root name or a mount
   target, reported as suspected copy-up or staging. To stay inside the
   invariant, the git reads run with `--no-optional-locks`
   (*read* — it prevents the index refresh that `git status` otherwise
   writes; worth one measurement when built).
3. **Partial teardown**: what stayed mounted and who holds it, from
   `/proc/*/cwd` and `/proc/*/fd` (C16, C30), by the same mountinfo
   scan as C1's check 5.
4. **Its own residue**: the kernel's `work/` is removed by `ply` itself
   — under the namespace mode it is user-owned mode-000 (*measured*),
   so a chmod precedes the removal; only what it cannot remove is
   reported.

`doctor` — the machine and the leftovers:

1. **Orphaned storage**: each `storage/<hash>/` carries a marker file
   (`.ply-target`: live path, config path) written at creation; `doctor`
   lists storages whose live composition no longer exists — the renamed-
   live case, which the hash cannot survive by design.
2. **Capability per mode** (exists today and reads correctly —
   *measured*), plus: locale (C29), an environment directory on a
   nosuid filesystem (correction 4), and a throwaway-overlay probe per
   mode that exercises whiteout and opaque (the lab's method, kept).
3. **Copy-up forensics** in both xattr namespaces — `user.overlay.*`
   confirmed real (correction 3), `trusted.*` to be confirmed at the
   first privileged composition.
4. **Prunable worktrees** with the same repair lines as `down`, because
   `doctor` is where you look three weeks later.

`status` is C1's verification pass run read-only, with three honest
words: *up*, *partly up*, *down*. One note the modes force: under the

## C7 — what the tool refuses rather than attempts

The consolidated list; each entry names its source. Everything here is
a refusal with a reason and, where the user must act, the exact
commands.

Before mounting:
- overlap not in `allow_overlap` — the gate (A4), mount-target-covered
  names exempt (B5);
- a declared order where an earlier target lies inside a later target
  (B6, and C1's static check);
- a mount target outside the live tree (C1);
- a missing target (C10) — including `.git/info/exclude`, with the two
  commands printed (C4);
- source/target type mismatch (C13);
- a source or root entry that is a symlink (C12, §8);
- a name containing a newline — inexpressible in an exclude and
  ambiguous in a report (Part D);
- a ply nested inside another ply, or `live` inside either repository;
- a second composition on the same upper — the lock and the scan (C1,
  C8; the kernel will not refuse it for you: *measured*);
- inventory violations: a new lower root entry, a type change (A12/§8);
- no inventory yet — first run: refuse and name `ply accept`, since an
  `up` that generated it would swallow the signal (A12);
- a workdir on a different filesystem than the upper (C6), or an
  environment whose locked flags the mode cannot reproduce
  (correction 4);
- a configured step that would run with privileges it must not have
  (C5).

After mounting: any failed verification from C1 — identity, polarity,
content, propagation, count, ownership — refuses the whole composition,
reverse teardown, named check.

## C8 — the git leak

Nothing prevents it, and per A10 nothing will: `git add -f` reads the
workspace file through the merged tree and stages its bytes; a hook in
`.git/hooks/` would never run (`core.hooksPath`, unchanged on both
repositories — re-checked today), and the hooks-bind idea from the
first attempt is dead — the owner ruled it outside the tool's remit,
and under the privileged mode it would change which hooks run
machine-wide.

What detection is worth, stated precisely: **the point of no return for
a shared history is `push`, not `commit`.** A leak caught at `down` —
the report in C6 — is usually still free: the user reverses it with a
reset in `code/`, with the composition down, entirely inside the
division of labour. And the last automated gate before that point of no
return, the pre-push hook, now measurably runs in both modes
(correction 1). That is the whole answer; there is no genuinely good
prevention idea to add.

## One addition worth pricing: read-only binds over the lower's root names

Not in Part C, but the evidence argues for it and it costs no settled
decision. In the steady state the lower's root is a handful of names
(the container directory, `CLAUDE.md`, `AGENTS.md`, `.claude`,
`.gitignore`). Under the redesign as written, editing `live/CLAUDE.md`
copies it up into the code repository silently, and the gate reports it
only at the **next** `up` — detection, where `model.md` §3's own
principle is loud-and-immediate failure.

Binding each non-target, non-allow-listed lower root name read-only
over the merged tree restores exactly the behaviour the proof of
concept measured and passed on — `01-mounts.txt` is precisely this
pattern, and `04-copyup-negative.txt`'s thirteen `EROFS` refusals are
its effect; the lab reproduced the refusals through the current binary
today. Steady-state cost: **three to four binds** (`.claude` is already
the C3 store, `.gitignore` is allow-listed). It composes and writes
nothing, so A9 is untouched; it is not the filtered view returning —
no git, no private view directory, no per-file binds. The owner may
still prefer detection-only; this is the one-paragraph case for
prevention at its post-migration price.

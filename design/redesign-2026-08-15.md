# Redesign, 2026-08-15

**Status: agreed in conversation, not yet merged into `model.md`, not
built.** This document records a simplification the owner worked through
on 2026-08-15. Where it disagrees with `model.md`, this document is the
newer decision — but `model.md` has not been rewritten yet, so both
exist, and the contradiction is deliberate and temporary.

`constraints.md` is unaffected. Nothing here contradicts a measured
constraint; several decisions below are *consequences* of one.

---

## 1. What changes

| | `model.md` | here |
|---|---|---|
| overlay layers | several lowers, precedence by `tree:` order | **one lower** (workspace), one upper (code) |
| what a layer contributes | what git tracks in it, bound name by name (the *filtered view*) | **the raw directory** — no filtered view, no per-name binds |
| roles | declared: `role: base \| layer \| bind` | **implied by where the repository is referenced** |
| hiding a lower entry | excluded from the filtered view | a bind over it, or nothing |
| writable holes | declared per path, placeholder + rw bind, type-correct | ordinary `mount_rw` entries |
| `.git/info/exclude` | generated *into* the code repository | generated into a temp file and **mounted over it** |
| pre-commit hook | the boundary in git terms | **dropped** — see §6 |
| overlap between base and lower | warned about until acknowledged | **blocks startup** — see §4 |

The filtered view is what most of the machinery in `model.md` §5 and §6
existed to build. Dropping it removes the assembled directories, the
type-correct holes, and the per-name bind explosion. It also gives up
what the filtered view bought — see §7, *What this costs*.

## 2. Shape

An **environment** directory holds the repositories, the configuration
and the generated stores:

```
$ENV/                        # e.g. ~/dev
├── .ply/
│   ├── config.yml
│   ├── work/<live-hash>/    # DISPOSABLE: overlay workdir, generated files
│   └── storage/<live-hash>/ # PERSISTENT: holds real work, never removed
├── diet-coach/              # code    (upper)
├── diet-coach-workspace/    # workspace (lower)
└── diet-coach-live/         # merged
```

The two stores must not share a naming scheme or a parent, because their
lifecycles are opposite: `work/` may be garbage-collected whenever
nothing is mounted; `storage/` holds unfinished worktrees and machine-local
state and may **never** be removed by the tool (`model.md` §6).

Inside `storage/`, the target's path is **mirrored**, not escaped:

```
storage/<live-hash>/.claude/worktrees/
storage/<live-hash>/.claude/settings.local.json
```

Escaping (`%2F`) was considered and rejected: a path component is limited
to 255 bytes, and `%2F` is three bytes per separator, so a deep target
overflows one component. Mirroring keeps every component a component, so
`NAME_MAX` holds exactly as it does in the live tree.

`<live-hash>` is derived from the live path (short, 8–12 hex), not random,
so an orphan left by a crashed run can be attributed.

## 3. Configuration

Semantics, not syntax — the file may be YAML, TOML or anything else.

```yaml
env: /home/dlaszlo/dev
merged: diet-coach-live          # $ENV/$MERGED

repositories:
  - { name: workspace, path: diet-coach-workspace }
  - { name: code,      path: diet-coach }
  - { name: registry,  path: registry }

overlayfs:
  lower: [workspace]             # a list, even though only one is supported today
  upper: code

allow_overlap: [README.md]
read_only:
  - .claude/important.txt
  - important_dir
mount_rw:
  - { source: "code/.git",           target: ".git" }
  - { source: "registry/.registry",  target: ".registry" }
mount_ro:
  - { source: "workspace/.claude/rules", target: ".claude/rules" }
```

Two rules about the file:

- **Mounts run in file order.** Nesting genuinely depends on order — a
  writable `.claude/` must be mounted before a read-only island inside it.
- **Everything else is a set, not a sequence.** `allow_overlap`,
  `read_only` and the like are unordered. One rule that only sometimes
  bites is worse than two honest ones.

`lower:` stays a list even while only one entry is accepted. Refusing a
second one with a clear message costs nothing; a scalar would foreclose
the general-workspace-plus-project-workspace case that the README names
as a goal.

## 4. The overlap gate

At `up`, before mounting: if a name exists in **both** the lower and the
upper and is not in `allow_overlap`, the environment **does not start**.

- It applies to **directories as well as files.** A directory overlap is
  a merge, which is a real decision, not a detail.
- Inside an allow-listed directory the check **descends**: a file present
  on both sides within a merged directory is exactly the trace of a
  copy-up, which is what we most want to catch.
- **There is no `--force`.** The escape hatch already exists and is
  called `allow_overlap`: the same decision, but recorded, diffable, and
  still legible in six months. Two ways to say one thing, one of which
  forgets, is not a choice — it is a weakening. It cannot wall anyone in,
  because `code/` and `workspace/` are ordinary directories on disk,
  reachable without the tool.

**The intended steady state is no overlap at all.** `allow_overlap` is a
last resort for a name that genuinely must exist on both sides, not a
menu option of equal standing — removing the overlaps is one of the
things the migration exists to do. That is what makes a gate with no
`--force` tolerable: after migration it should almost never fire, and
when it does, something really did change.

Because there is no bypass, **the refusal message is load-bearing**: it
must name the path, say what is on each side, and give both ways out (fix
it by hand, or add it to `allow_overlap`). "Overlap detected" is not
acceptable.

The gate fires at `up`, which means it fires while the composition is
**down** — the one moment when repairing the repositories by hand is safe.
That is a property to preserve, not a coincidence.

## 5. Git wiring without touching the repository

The exclude list is generated at `up` into a file under `work/`, and that
file is **mounted over** the upper's `.git/info/exclude`. The repository's
own file is never edited.

Derivation:

```
exclude = (the lower's entries) − (allow_overlap) + (every mount target)
```

- A lower entry that does **not** overlap is excluded **by name**, whether
  file or directory. One line covers a whole directory, and it does not
  need regenerating when the workspace gains a file inside it.
- File-level enumeration is needed **only inside allow-listed
  directories**, where base and lower content mix. There, recurse.
- An `allow_overlap` entry is itself never excluded. For a file the
  exclusion would be inert anyway (git ignores ignore-rules for tracked
  files); for a directory it would actively hide the base's own untracked
  files.
- Mount targets are excluded by their **target** path, whatever its type.
- The lines are **gitignore patterns**, not names: `*`, `?`, `[`, `]`,
  `!`, `#`, trailing spaces and `\` must be escaped, or a file named
  `README[draft].md` will mean something else.

Coarse exclusion is safe precisely **because the gate re-checks every
`up`**: if the base later grows its own entry under a coarsely excluded
name, the next start reports it as an overlap rather than hiding it.

**The invariant this produces — and the point of the whole section:**

> `ply` only ever composes. It never modifies a repository.

Reading is not modification: `git ls-files`, `git check-ignore` and
friends are fine. The line is at writing. Because of this, the promise
that `code/` is untouched becomes **measurable** — after `down`, the
repository is byte-identical, `.git` included.

## 6. No pre-commit hook

`model.md` §8 calls the pre-commit hook the boundary in git terms. That
is now dropped, for a reason that is measured rather than argued:

**Both real repositories set `core.hooksPath`** — the code repository to
an absolute path (`/home/dlaszlo/dev/diet-coach/deploy/git-hooks`), the
workspace to a relative one (`scripts/hooks`). When `core.hooksPath` is
set, git looks **only** there; `.git/hooks/` is bypassed entirely. A hook
installed by `ply` would therefore never run: a protection that looks
installed and does nothing, which is worse than none.

Installing hooks would also break the invariant in §5, and it is git
manipulation — outside the tool's remit.

**State the consequence plainly:** nothing *prevents* a leak any more. The
read-only mounts stop writes, not reads, so `git add -f` can still read a
workspace file through the merged tree and stage its content into the code
repository. What remains is **detection**: the gate at the next `up`, and
the drift report at `down`. Anything that reaches the history cannot be
fixed retroactively — only rewritten, which is outside the tool.

## 7. What this costs

Honest accounting of what the filtered view was doing and what now
replaces it:

- **The lower's gitignored junk becomes visible.** `.mypy_cache`,
  `.pytest_cache`, `.obsidian` and the workspace's `.git` all appear in
  the merged tree. `.git` is handled by a bind; the rest is not.
- **Worse than visible: writable-by-copy-up.** A tool writing into a
  lower-provided cache directory does not fail — the overlay copies it up
  into the code repository. The filtered view made these paths read-only
  binds, so they failed loudly. Now they succeed quietly, in the wrong
  place. *This is the sharpest cost of the simplification and needs an
  answer.* A cheap candidate: warn at `up` about lower entries that the
  lower's own git ignores.
- **Reserved names are no longer derived from git.** They are now derived
  from the lower directory listing, which includes junk.

## 8. Inventory (lockfile)

A generated record of the root entries of the lower and the upper, with
**type** — file, directory, or **symlink and its target**. Type matters:
a name that is a file on one side and a directory on the other is an
error, and a root entry that becomes a symlink is dangerous, because a
bind follows it and would pull in content from anywhere on the machine.

- **Generated by an explicit command** (`ply accept` proposed), never by
  `up` — an `up` that silently refreshed it would swallow the very signal
  the file exists to raise.
- **A separate file beside the configuration**, not inside it: the
  configuration states intent; this is a snapshot of inputs.
- **Sorted**, so its diff is reviewable.
- New lower root entry → **blocks**. Type change → **blocks**. Entry
  disappeared, or upper-side change → **warns**.

It shares one enumeration with the exclude list, so the two cannot drift
apart.

## 9. Division of labour

- **The user deletes; `ply` checks.** The tool never deletes a file, a
  checkout or a branch, and never commits. When a leaked file must be
  removed from the code repository, the user removes it and commits the
  removal — in `code/`, with the composition down.
- **Deleting through the live tree is a trap.** If the name exists in both
  layers, removing it from the merged view writes a **whiteout** — a `0:0`
  character device — into the code repository's working tree (C4), which
  git cannot represent and refuses to add (C28), and which then has to be
  removed by hand.
- **`up` may refuse; `down` may only report.** A refusing `down` would
  wall the user in behind a composition they cannot take apart. Drift and
  leaks are reported at `down` as well as `up`, because the end of a
  session is when the cause is still fresh.

## 10. Open — to be worked out

1. **Externalising the exclude generation.** After the simplifications
   above, git appears in the core in exactly one place: this list.
   Contribution is now a directory listing, the gate compares directories,
   the inventory stats them — none of it needs git. If the generation
   becomes a configured step (a command run at a named phase, consuming a
   list `ply` materialises), the core contains no git at all, and git
   becomes one integration among several. Three things to settle:
   - **Privilege.** A configured command plus a privileged `up` means
     whoever can edit `config.yml` runs code as root. Configured steps
     must run as the invoking user, after dropping privilege.
   - **Phase points.** The generated file must exist before it is
     mounted, so at least `prepare` / `mounted` / `pre-down` / `down`.
   - **Ship a default.** Configurable must not mean obligatory: the git
     integration should work out of the box.
2. **The copy-up-into-a-lower-cache problem** in §7.
3. **`.claude/` specifically.** It mixes tracked workspace content with
   unpredictable runtime writes, and the set of runtime names cannot be
   enumerated in advance. The shape that survives review so far: mount a
   writable store over `.claude/` first, then read-only islands
   (`.claude/rules`, `.claude/agents`) inside it — which is also the best
   justification for mounts being order-dependent. Not yet decided.

So the gate blocks on day one, five times over. That is intended: it is
what will force the repository rearrangement the owner already decided on

workspace's docs under `workspace/docs`, give `.registry` its own
repository). None of that has been done yet.

`.registry` is currently **tracked inside the workspace repository**, not
a separate repository — `mount_rw` from a `registry` repository has no
source to point at until it is split out.
